# Вход, роли и миграция Knowledge Desk

## Запуск с Supabase

FastAPI подключается к базе по `KNOWLEDGE_DESK_DATABASE_URL` и проверяет сессию через `KNOWLEDGE_DESK_SUPABASE_URL` и `KNOWLEDGE_DESK_SUPABASE_PUBLISHABLE_KEY`. Положите серверные переменные в `backend/.env`. Для PostgreSQL используйте роль с членством в `knowledge_desk_runtime`, Session pooler и проверку сертификата `sslmode=verify-full`. [Подключение к Supabase PostgreSQL](https://supabase.com/docs/guides/database/connecting-to-postgres) · [Проверка сертификата](https://supabase.com/docs/guides/platform/ssl-enforcement)

```powershell
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
.\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --loop backend.app.postgres:selector_loop --env-file backend/.env --host 127.0.0.1 --port 8000
```

Во втором терминале из `frontend` запустите `npm run dev`. [Открыть Knowledge Desk](http://127.0.0.1:5173). Для выхода используйте кнопку в навигации. Когда выданный Supabase токен истечёт, приложение попросит войти снова. Для HTTP-разработки открывайте фронтенд и API на одном имени хоста, `127.0.0.1`.

## Права участников

| Роль | Документы | Заявки |
| --- | --- | --- |
| Читатель | Читает общие документы | Создаёт и читает свои заявки |
| Редактор | Читает общие и свои документы. Загружает, редактирует, удаляет и открывает доступ к своим документам | Создаёт и читает свои заявки |
| Оператор | Читает общие документы | Работает с общей очередью, отвечает, меняет статус и редактирует ответы |

Для регистрации участника создайте пользователя в Supabase Authentication и назначьте роль в `knowledge_desk.members`. Вход разрешается только аккаунтам с такой записью. Роль и владелец берутся на сервере. Переключатель «Доступен всем участникам» находится в карточке документа редактора. Документ, PDF, поиск и открытие цитаты сверяют один и тот же доступ. Для ранее сохранённых источников в черновике сервер сверяет доступ заново.

Таблицы находятся в приватной схеме `knowledge_desk`. Роль приложения может читать список участников, а назначение ролей выполняется отдельно владельцем проекта. [Доступ к приватным схемам Supabase](https://supabase.com/docs/guides/api/securing-your-api)

## Перенос из SQLite

1. Примените SQL из `supabase/migrations` в тестовом проекте. Проверьте, что назначаемый владелец уже имеет роль редактора в `knowledge_desk.members`.
2. Остановите запись в старую базу и запустите команду из корня репозитория. Перенос работает на копии SQLite и выполняет запись в PostgreSQL в одной транзакции. При совпадении ID он сверяет поля, конфликт вызывает откат.

```powershell
.\.venv\Scripts\python.exe -m dotenv -f backend/.env run -- .\.venv\Scripts\python.exe -m backend.migrate_supabase --owner UUID_РЕДАКТОРА
```

Точное совпадение с учебным манифестом даёт общий доступ, остальные унаследованные документы закрыты и принадлежат назначенному редактору. Сначала SQLite-импорт сохраняет байты прежних PDF в PostgreSQL. Затем их можно перенести в приватный Storage, а старые векторы в pgvector.

Ожидающие подтверждения черновики с локальными контрольными точками требуют завершения или отмены до миграции. Новые контрольные точки пишутся в PostgreSQL. Старая SQLite остаётся исходной копией. Старый локальный режим подходит для проверки на loopback, запуск с `KNOWLEDGE_DESK_DATABASE_URL` требует настроенного Supabase Auth.

## Приватное хранилище PDF

Новые PDF и сканы хранятся в бакете `knowledge-desk-originals` с лимитом 10 МиБ на PDF. В PostgreSQL остаются внутренний ключ файла, контрольная сумма и смещения для цитат. Сервер читает бакет через отдельный аккаунт Supabase Auth с `app_metadata.knowledge_desk_storage = "originals"`. Настройки этого аккаунта `KNOWLEDGE_DESK_STORAGE_EMAIL` и `KNOWLEDGE_DESK_STORAGE_PASSWORD` хранятся в серверном `backend/.env`. Права на чтение, запись и удаление распространяются только на этот бакет. [Приватные бакеты](https://supabase.com/docs/guides/storage/buckets/fundamentals) · [Политики доступа Storage](https://supabase.com/docs/guides/storage/security/access-control)

Оригинал открывается по прежнему `/documents/{id}/original.pdf`. Ссылка `#page=N` выбирает страницу в просмотрщике PDF, а `?page=N` отдаёт указанную страницу для предварительного просмотра. FastAPI сначала проверяет авторизацию и доступ к документу, затем читает оригинал и проверяет его контрольную сумму. Чужой закрытый документ возвращает `404`, а прямой адрес объекта в Storage доступен только служебному аккаунту.

После применения SQL-миграций и настройки служебного аккаунта команду можно повторить для оригиналов, сохранённых ранее в PostgreSQL. Запускайте из корня проекта:

```powershell
.\.venv\Scripts\python.exe -m dotenv -f backend/.env run -- .\.venv\Scripts\python.exe -m backend.migrate_pdf_storage
```

Команда скачивает записанный файл и сравнивает байты с исходником, затем одной транзакцией сохраняет ссылку и удаляет встроенную копию. При удалении документа сервер записывает задачу очистки Storage. Если Storage временно недоступен, задача остаётся в PostgreSQL. Сервер повторяет очистку при следующем запуске или удалении документа. При необходимости ту же команду можно выполнить с `--cleanup-only`.

На момент переключения в рабочей базе и старой SQLite было 0 оригиналов. На вымышленном PDF перенос сохранил прежний URL, все байты и выдачу второй страницы на работающем API. Для нового скана с реальным распознаванием кириллицы цитата указала вторую страницу и открыла соответствующий фрагмент PDF. Второй аккаунт получил `404` по прямому URL закрытого PDF и по URL его страницы. Прямой URL приватного объекта в Storage также не выдал файл. После отзыва общего доступа тот же URL снова вернул `404`. Удаление тестовых документов очистило оба объекта из бакета.

## Индекс pgvector

В режиме Supabase текст, вектор, ID фрагмента, смещения и номер страницы хранятся в приватной таблице `knowledge_desk.rag_chunks`. PostgreSQL проверяет права и текущую редакцию документа перед сортировкой пяти результатов по косинусному расстоянию. Прямое открытие цитаты проверяет те же права. Файлы Chroma и манифест используются при переносе. На рабочем сервере отдельно нужен кэш весов E5 для расчёта эмбеддинга запроса. [pgvector в Supabase](https://supabase.com/docs/guides/database/extensions/pgvector)

Остановите запись в старый индекс на время переноса. Из корня репозитория после применения SQL-миграций:

```powershell
.\.venv\Scripts\python.exe -m dotenv -f backend/.env run -- .\.venv\Scripts\python.exe -m backend.migrate_pgvector `
  --manifest-index 300=data/orbita-300-v1.chroma --manifest-index 400=data/chroma --manifest-index 600=data/orbita-600-v1.chroma
```

Скрипт сверяет ID, текст, метаданные и каждый компонент вектора. Новый импорт можно повторить с той же копией каталога и индексами. Конфликт содержимого по ID отменяет транзакцию. `KNOWLEDGE_DESK_CHUNK_SIZE` выбирает учебный профиль для новых запросов. Цитаты из всех перенесённых профилей открываются по исходному ID, пока у участника есть доступ к нужной редакции. Загрузка, редактирование и удаление обновляют каталог и векторы в одной транзакции.

В проекте Knowledge Desk перенесены **143 фрагмента**. В это число вошли 60, 41 и 25 учебных фрагментов для профилей 300, 400 и 600 и 17 фрагментов загрузок. На десяти контрольных вопросах профиля 400 первые пять результатов pgvector совпали с Chroma по ID и порядку. С полностью отключённым чтением локальных индексов API открыл четыре прежние ссылки, включая цитату загруженного документа. Читатель получил `404` на все 17 закрытых прежних цитат. На новом закрытом PDF два реальных аккаунта проверили источник, страницу, выдачу RAG, отзыв доступа и обновление фрагментов при редактировании. Для сравнения и поиска использовалась E5, генерация ответа была подменена.

## Проверка доступа

1. Войдите редактором и загрузите тестовый PDF с вымышленным фактом. Создайте заявку и скопируйте ссылку на неё. Задайте вопрос по PDF и скопируйте ссылку на найденный фрагмент.
2. Выйдите и войдите читателем. Проверьте, что заявка отсутствует в списке, прямые ссылки на заявку, PDF и цитату возвращают `404`, а модель не получает закрытый фрагмент.
3. Назначьте тестовому аккаунту роль оператора. В общей очереди проверьте отправку ответа и смену статуса. Закрытый PDF по-прежнему должен возвращать `404`.

Сценарий API с подменой генерации воспроизводится командой `.\.venv\Scripts\python.exe -X utf8 -m pytest -q backend/tests/test_supabase_access.py`.

## Результат переноса

В отдельный проект Knowledge Desk перенесены 23 документа, 1 запись об индексированной загрузке, 9 заявок и 1 ответ. Повторный запуск сверил содержимое каждой записи по исходному ID. Владелец получил 20 общих и 3 закрытых документа. В исходной базе отсутствовали PDF, черновики и события доставки. Сервер подключается к PostgreSQL с проверкой имени и сертификата.

Два реальных тестовых аккаунта прошли вход. Для читателя чужая заявка, закрытый PDF и прямая ссылка на цитату вернули `404`. Закрытый фрагмент не попал в генерацию, а после отзыва доступа исчез и из сохранённого черновика. После назначения роли оператора тестовый аккаунт ответил на заявку и закрыл её, а закрытый PDF оставался недоступен. Проверка входа и выхода в Chrome пройдена на ширине 1440 и 390 пикселей. В тесте использовались фиксированные векторы и подмена генерации. Поиск в Chroma и проверка прав выполнялись в приложении. Тестовые аккаунты и их записи удалены после проверки.

Supabase Security Advisor отметил проверку паролей по базе утечек. Она доступна с Pro, отдельный проект создан на бесплатных условиях. [Защита паролей в Supabase](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection)
