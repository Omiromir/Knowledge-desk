# Тестовая доставка заявки в n8n

В [workflow v2](n8n/request-created.test.workflow.json) Webhook проверяет заголовок, IF проверяет JSON, а узел Postgres вызывает `knowledge_desk.record_n8n_receipt` в Supabase. Эта функция сохраняет одну квитанцию на `event_id`. Повтор с теми же данными возвращает исходную квитанцию с первым `execution_id`. Тот же ID с другим `request_id` получает `409 event_conflict`. Остальные поля события фиксированы и проходят проверку до запроса в Postgres.

## Запуск теста

1. В Supabase Knowledge Desk уже применена [миграция журнала](../supabase/migrations/20261120183946_n8n_receipts_access.sql). Роль `knowledge_desk_n8n` даёт право вызывать одну функцию квитанций. Для отдельной установки администратор создаёт логин с этой ролью и случайным паролем.
2. Импортируйте workflow v2 в тестовый n8n. В **Test webhook** выберите credential **Header Auth** для `X-Knowledge-Desk-Secret`. В **Record or read receipt** выберите credential **Postgres** с реквизитами из локального `backend/.env.n8n`. Используйте хост и порт **Session pooler**, имя базы `postgres`, логин с суффиксом проекта, SSL **Require**, сертификат из [backend/supabase-ca.crt](../backend/supabase-ca.crt) и выключенное **Ignore SSL Issues**. Пароль храните в credential n8n. [Учётные данные Postgres в n8n](https://docs.n8n.io/integrations/builtin/credentials/postgres/) · [Подключение к Supabase](https://supabase.com/docs/guides/database/connecting-to-postgres).
3. В терминале FastAPI задайте `KNOWLEDGE_DESK_N8N_TEST_URL` с точным путём `/webhook-test/knowledge-desk-request-created-v2` и `KNOWLEDGE_DESK_N8N_SECRET` со значением Header Auth. Допустимы HTTPS или HTTP на loopback и секрет из 32–128 печатных ASCII-символов без пробела.
4. В n8n нажмите **Listen for test event** для Test URL. В приложении откройте «Ответы» → «Помощник» → «Заявка на консультацию». Введите вымышленные имя и вопрос, подготовьте черновик и нажмите «Подтвердить».
5. В карточке заявки проверьте статус **«Доставка подтверждена»**, ID события и номер выполнения n8n. [Документация тестового webhook n8n](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/).

```powershell
$env:KNOWLEDGE_DESK_N8N_TEST_URL = 'http://127.0.0.1:5678/webhook-test/knowledge-desk-request-created-v2'
$env:KNOWLEDGE_DESK_N8N_SECRET = Read-Host 'Тестовый секрет из credential n8n' -MaskInput
.\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --loop backend.app.postgres:selector_loop --env-file backend/.env --host 127.0.0.1 --port 8000
```

Внешнее событие содержит `event_id`, `request_id`, `type: "request.created"` и `data: {"kind":"consultation","test":true}`. Имя, вопрос, документы и владелец остаются в приложении. Ответ подтверждает доставку, если содержит `status: "accepted"`, те же оба ID и `execution_id`. Тайм-аут одного HTTP-вызова составляет **5 секунд**, перенос на новый адрес по редиректу выключен.

## Проверка `unknown` и повтора

1. Во временной тестовой версии workflow вставьте **Wait** на 8 секунд между **Record or read receipt** и **Return receipt**. Включите ожидание Test URL и подтвердите новую вымышленную консультацию. Квитанция запишется в Postgres, а карточка покажет «Доставка не подтверждена» после тайм-аута FastAPI.
2. Восстановите прямую связь между узлами и снова включите ожидание **того же Test URL**. В карточке заявки нажмите **«Повторить доставку»**. Заявка останется одна, `event_id` сохранится, а в карточке появится статус «Доставка подтверждена» с номером первого выполнения.
3. В SQL Editor Supabase проверьте, что в `knowledge_desk.n8n_receipts` для показанного `event_id` одна строка. Два HTTP-вызова могут дать два выполнения webhook, приём события фиксируется один раз.

Повтор также доступен через `POST /requests/{id}/delivery/retry` без тела запроса. Если ответ потерялся или слушатель Test URL выключен во время повтора, статус остаётся `unknown`. После повторного включения слушателя можно попробовать снова. Пока идёт попытка, кнопка блокируется. Право на повтор проверяет сервер.

## Перенос старого журнала

Остановите приём событий на старом workflow. Из прежней PostgreSQL выгрузите строки [старой таблицы](n8n/create-receipts.sql) в JSON. Здесь `legacy_n8n` — имя подключения psql из личного файла настроек.

```powershell
psql -X -At 'service=legacy_n8n' -c 'SELECT COALESCE(json_agg(r ORDER BY event_id), json_build_array()) FROM public.knowledge_desk_test_receipts AS r' |
    Set-Content -Encoding utf8 'output/n8n-receipts.json'
if ($LASTEXITCODE -ne 0) { throw 'Экспорт журнала завершился ошибкой' }
.\.venv\Scripts\python.exe -m backend.migrate_n8n_receipts output/n8n-receipts.json
```

Импорт использует `KNOWLEDGE_DESK_N8N_DATABASE_URL` из переменной окружения или `backend/.env.n8n`. Он сохраняет все три исходных поля. Повторный импорт сверяет уже сохранённые квитанции. Если хотя бы одна отличается, вся транзакция откатывается. После переноса включите обновлённый workflow на том же v2 Test URL.

У журнала включена защита строк (RLS). Прямой доступ оставлен администратору базы. У n8n есть только право вызвать функцию, которая записывает новую квитанцию или возвращает исходную.

## Хранение и доступ

| Слой | Где хранится | Кто читает |
|---|---|---|
| Ввод, ответ и результат инструмента | Текущий экран браузера. `/ask` и `/ai/tools` обрабатывают один запрос без серверного архива беседы | Текущий экран |
| Черновик и ход рассуждения приложения | `consultation_drafts` и checkpoint LangGraph | Владелец из серверного контекста |
| Подтверждённая заявка и ответы | `requests`, `request_replies` и квитанция подтверждения в `consultation_receipts` | Владелец заявки |
| Доставка | `integration_events` с уникальными ID события и заявки | Владелец заявки через `GET /requests/{id}/delivery` |
| Журнал приёма n8n | `knowledge_desk.n8n_receipts` в Supabase с первичным ключом `event_id` | Администратор читает таблицу, workflow получает квитанцию через выделенную функцию |

Кнопка «Новый разговор» сбрасывает ввод и текущие ответы в браузере. Сохранённый черновик можно снова открыть по его адресу. Подтверждённая заявка и квитанция доставки остаются в базе и читаются после перезапуска. Владелец определяется по сессии Supabase Auth. Имя в форме остаётся полем заявки. [Роли и миграция данных](supabase-migration.md).

## Состояния и граница гарантии

| Состояние | Когда появляется | Что делает повтор подтверждения |
|---|---|---|
| `pending` | Заявка, квитанция подтверждения и событие зафиксированы одной транзакцией. HTTP-вызов ещё не начался | При валидной конфигурации делает первую попытку |
| `unknown` | Попытка захвачена в базе, получен тайм-аут, ошибка транспорта или непроверяемый ответ | Возвращает событие для сверки по `event_id` |
| `failed` | Получен определённый отказ, например конфликт идентификатора | Возвращает сохранённую ошибку |
| `delivered` | Получена квитанция с двумя совпадающими ID | Возвращает сохранённую квитанцию |

FastAPI атомарно захватывает попытку в базе. При падении процесса захват истекает через 7 секунд от начала попытки. Следующую попытку запускает человек. Повтор подтверждения возвращает сохранённое состояние. Отдельный повтор доставки разрешён для `unknown`, если исходная попытка была отправлена на тот же v2 Test URL. Старые `unknown` с `/webhook-test/knowledge-desk-request-created` сверяйте вручную по ID. При смене базы квитанций временно остановите приём событий, импортируйте журнал целиком и сохраните прежний URL v2. Храните запись, пока событие можно повторить.

Первичный ключ и одна операция `INSERT … ON CONFLICT` обеспечивают одну логическую запись даже при параллельных вызовах. В этом workflow действие заканчивается записью о приёме в Postgres. Для будущего письма или вызова ещё одного сервиса потребуется отдельная идемпотентность по `event_id`. [Семантика `ON CONFLICT` в PostgreSQL](https://www.postgresql.org/docs/current/sql-insert.html).

Экспорт workflow выключает сохранение ручных выполнений в списке n8n. На проверенной версии n8n помечает запись удалённой, а сырые данные могут оставаться в базе до очистки. Заголовок авторизации также доступен в редакторе во время теста. Используйте временный секрет и сверяйтесь с журналом квитанций, в котором хранятся только идентификаторы. [Настройки сохранения выполнений n8n](https://docs.n8n.io/workflows/settings/).

```powershell
.\.venv\Scripts\python.exe -X utf8 -m pytest -q backend/tests/test_integration_delivery.py
```

Тесты с подменным транспортом проверяют отсутствие POST до подтверждения и при отмене, точность квитанции, HTTP 500, тайм-аут, потерю ответа после приёма события, два параллельных запроса, восстановление после перезапуска, повтор с тем же телом и изоляцию владельцев.

## Проверка после переноса в Supabase

20 ноября 2026 года перенесены следующие тестовые квитанции. Повторный импорт оставил ровно две строки. Пробный импорт с новой записью и конфликтующей старой квитанцией откатил обе операции.

| Источник | `event_id` | `request_id` | Первое выполнение |
|---|---|---|---|
| Журнал PGlite, v2 | `857037a4-5641-4d2d-b06c-1ce4291314e4` | `f567b60f-5466-4eed-a18c-fa552398a5d5` | `1` |
| Архив теста, v1 | `346a97d8-75b2-4cce-9d90-e01ae035ccfe` | `57bd551d-169a-4c8d-85e6-2af1a8a12ced` | `2` |

На отдельном n8n 2.48.7 с тестовым webhook и настоящей базой Supabase Playwright подтвердил вымышленную заявку. После того как n8n записал квитанцию и вернул HTTP 200, тестовый прокси оборвал соединение. Карточка показала `unknown`. Кнопка «Повторить доставку» отправила то же JSON-событие, получила исходную квитанцию с выполнением `1` и показала `delivered`. Повторное открытие карточки сохранило статус.

Для нового тестового события `0488de21-e34a-414c-b4e4-50cf02b681a9` в Supabase проверены одна заявка, одно событие приложения и одна квитанция n8n. После проверки данные нового теста удалены. Обе перенесённые квитанции вернулись через обновлённый webhook с исходными ID и номерами выполнения и остались в журнале. Тот же `event_id` с другим `request_id` получил HTTP 409. Учётка n8n не могла напрямую изменить таблицу или прочитать заявки, у обычной роли `authenticated` отсутствовало право вызова функции.

## Исторический прогон v2

20 ноября 2026 года в локальном n8n 2.48.7 с постоянным тестовым журналом PGlite оборвали соединение после первого ответа n8n. В карточке появился `unknown`. Попытка до повторного запуска Test URL сохранила `unknown`, после запуска кнопка вернула исходную квитанцию с выполнением `1` и тем же событием `857037a4-5641-4d2d-b06c-1ce4291314e4`. Два корректных вызова дошли до получателя и вернули одинаковую квитанцию. В приложении осталась одна заявка, в журнале n8n одна строка. Вызов с тем же `event_id` и другим `request_id` получил `409`. Playwright проверил карточку на 1400 и 390 px, клавиатурный повтор и блокировку повторного нажатия до ответа.

## Исторический прогон v1

20 ноября 2026 года n8n 2.48.7 принял вымышленную консультацию из UI через Test URL. Неправильный секрет получил `403`, событие без `request_id` получило `400`. У приложения и выполнения n8n совпали `event_id` и `request_id`. После «Нового разговора» поле помощника было пустым, а заявка оставалась в «Заявках» вместе с квитанцией. После перезапуска FastAPI и повторного подтверждения сохранились одна заявка, одно событие и та же квитанция. [Квитанция реального тестового выполнения](n8n/test-receipt.json).

Прошли 174 серверных теста, сборка и линтер. В Playwright проверены карточка и подтверждение на 1400 и 390 px. Отдельно подменён статус доставки на `unknown`: карточка сохранила заявку и предложила сверку по ID.
